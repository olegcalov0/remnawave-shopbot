## 1. Исправленные баги (найдены по логам прод-инцидента + тестам)

### BUG-001 [Blocker] Потеря данных vpn_keys при restore старой БД

- **Severity:** Blocker (порча данных пользователей).
- **Окружение:** прод, restore legacy-бэкапа; воспроизведено в unit.
- **Предусловие:** загружается БД старой версии (узкие таблицы, нет колонок
  `created_at`/`updated_at` в `vpn_keys`).
- **Шаги:** restore → `run_migration` → `_ensure_vpn_keys_schema` →
  `_rebuild_vpn_keys_table` (ALTER RENAME + CREATE + INSERT) — rebuild и
  последующие legacy-шаги выполняются в одной незакоммиченной транзакции;
  поздний шаг (`button_configs`) падает → `conn.rollback()` откатывает INSERT,
  но sqlite оставляет рассинхронизированное состояние → `vpn_keys` пустая,
  часть данных в `vpn_keys_legacy`.
- **Фактическое поведение (до фикса):** `vpn_keys rows: 0`, таблица
  `vpn_keys_legacy` с данными остаётся в БД.
- **Ожидаемое:** данные сохраняются (ТЗ этап 8: «не удалять»).
- **Фикс:** немедленный `conn.commit()` сразу после шага `vpn_keys_schema`
  (database.py); страховка `_recover_vpn_keys_legacy()` — аварийный перенос
  данных из зависшей `vpn_keys_legacy` по пересечению колонок, если
  полу-rebuild всё же случился.
- **Регрессия:** `tests/test_restore_repair.py::test_user_data_preserved`.

### BUG-002 [Critical] Дашборд падает после restore старой БД

- **Severity:** Critical (отказ страниц админки).
- **Логи прод:** `no such column: u.registration_date`, `no such column:
  created_date`, `no such column: amount_rub`, `no such column: p.months`
  на `/dashboard/trials.partial` и во всех запросах статистики.
- **Причина:** восстановленная БД старой версии не имела поздних колонок;
  `run_migration` добавляет лишь часть, а шаги падали на отсутствующих
  зависимостях и молча откатывались.
- **Фикс:** новый модуль `schema_repair.py` — канонический перечень колонок
  всех core-таблиц; `repair_schema()` добавляет недостающие колонки
  (`ALTER ADD COLUMN`), вызывается в конце `run_migration` и в
  `restore_from_file` для legacy-источников. Legacy-колонки `vpn_keys`
  (`created_date`, `expiry_date`, `xui_client_uuid`) в repair НЕ добавляются —
  их обрабатывает только штатный rebuild (иначе repair сам «ломал» таблицу,
  BUG-001 обострялся).
- **Регрессия:** `tests/test_restore_repair.py` — все запросы дашборда
  (trials, transactions, статистика по дням, метрики покупателей, `p.months`)
  проходят на восстановленной старой БД.

### BUG-003 [Major] /premna 500 при недоступной панели Remnawave

- **Логи прод:** `jinja2.exceptions.UndefinedError: 'None' has no attribute
  'users'` на `/premna [GET]`.
- **Причина:** шаблон вычисляет `statistics.users[key]` даже когда
  `statistics=None` (блок лишь скрывается через CSS `hidden`).
- **Фикс:** безопасный `{% set statistics = statistics or {...дефолты...} %}`
  в `premna.html`; при ошибке API показывается error-блок с «—» в карточках.
- **Severity Major**, т.к. страница админки полностью недоступна при таймауте
  панели.

### BUG-004 [Minor] sqlite: «Cannot add a column with non-constant default»

- Найден при фиксе BUG-002: `ALTER ADD COLUMN ... DEFAULT CURRENT_TIMESTAMP`
  запрещён SQLite. `_constant_default()` в schema_repair заменяет на
  `TEXT DEFAULT ''`. Колонки существуют, запросы работают; NULL-значения
  не мешают агрегатам (`DATE('')` → NULL, GROUP BY корректен).

### BUG-005 [Trivial→исправлен] Кодировка install.sh/uninstall.sh

- Двойной mojibake (UTF-8→CP1251→UTF-8) после PowerShell-конвертации CRLF.
  Восстановлено обратной таблицей; `bash -n` OK, UTF-8 без BOM, LF.

### BUG-006 [Major] certbot --nginx не мог установить сертификат при чистой установке

- **Логи прод:** «Could not automatically find a matching server block».
- **Фикс:** `ensure_bootstrap_server_block()` — временный HTTP server block
  до certbot; при полученном, но неустановленном сертификате установка
  продолжается.

## 3. Открытые риски (требуют стенда B/C — живая панель и sandbox ПС)

1. **API-контракт Remnawave не проверен вживую** (TC-2.1–2.23): создание с
   `telegramId`, семантика `trafficLimitBytes=0`, склейка подписок на странице
   подписок, HWID-поведение между двумя пользователями пары (TC-2.19 —
   поведение панели неизвестно, может потребовать UX-решения).
2. **Платёжные вебхуки live** (TC-3.1–3.5 по каждой ПС): unit-покрытие
   идемпотентности есть, но реальные подписи/суммы каждой ПС не проверялись.
3. **Массовый перевод сквадов из UI** (TC-11.15): функция
   `move_pair_squads` есть, кнопки нет — официальное ограничение.
4. **Фильтры пользователей** (TC-11.16): API отдаёт данные, UI-фильтров нет —
   официальное ограничение.
5. **restore не откатывает панель Remnawave** (TC-12.9): поведение by design;
   предупреждение в flash-сообщении и в `last_restore_info` есть; snapshots
   в бэкапе позволяют сверить состояние вручную.
