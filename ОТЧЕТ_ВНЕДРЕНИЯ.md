# ОТЧЕТ О ВНЕДРЕНИИ: докупка трафика, гибридные подписки и надёжная обработка оплат

Проект: `remnawave-shopbot`. Доработка выполнена по ТЗ `TZ.md` (этапы 0–9).
Все этапы реализованы в порядке, требуемом ТЗ. Тесты запускаются одной командой:

```
python -m pytest tests/ -q
```

Результат финального прогона: **60 passed** (Python 3.11, Windows; pytest 9.0.2, pytest-asyncio 1.4.0).

Важно: запуск модулей с `paramiko`/`aiogram` требует установленных зависимостей проекта
(`pip install -e .` либо Docker-окружение); юнит-тесты нового домена этих пакетов не требуют.

### Схема данных (раздел 4 ТЗ)

Созданы таблицы с индексами:

- `traffic_purchase_packages` — индекс `(host_name, traffic_type, is_active, sort_order)`;
- `hybrid_subscription_pairs` — `UNIQUE(primary_key_id)`, индексы по user_id, `(host_name, status)`, telegram_id, обоим remnawave_user_id;
- `traffic_carry_balances` — `UNIQUE(key_id, target_role, traffic_type)`, `CHECK (remaining_gb >= 0)`;
- `traffic_purchases` — `UNIQUE(payment_id)`, индексы `(key_id, created_at DESC)`, `(user_id, status)`, `(status, updated_at)`, `target_remnawave_user_id`;
- `traffic_operations` — `UNIQUE(idempotency_key)`;
- `traffic_referral_rewards` — `UNIQUE(source_purchase_id)`;
- `payment_fulfillment_jobs` — `UNIQUE(payment_id)`, индекс `(status, next_attempt_at)`;
- `backup_runs`, `remnawave_state_snapshots` — индекс по `backup_run_id`;
- `bot_settings.schema_version = '2'` (минимально поддерживаемая при restore).

`PRAGMA foreign_keys = ON` в соединениях репозитория; переходы статусов — условные
UPDATE в `BEGIN IMMEDIATE`; `INSERT OR REPLACE` нигде в новом домене не используется.

Миграционный путь для существующей БД: `ALTER TABLE ADD COLUMN` с безопасными
default (`hybrid_enabled=0`, `traffic_purchase_enabled=0` и т.д.), поэтому после
миграции существующие хосты продолжают работать в обычном режиме (проверено тестом
`test_existing_db_migration_preserves_data`).

### Тесты (команда: `python -m pytest tests/test_migrations.py -q`)

- Чистая БД: все новые таблицы/индексы создаются — passed.
- Существующая БД: `users`/`vpn_keys`/`transactions`/`plans`/`xui_hosts` и данные сохраняются; хост после миграции `(hybrid_enabled=0, traffic_purchase_enabled=0)` — passed.

- `UNIQUE(payment_id)`, `UNIQUE(primary_key_id)`, уникальность carry, `UNIQUE(idempotency_key)` — passed (IntegrityError).
- Условный transition job/purchase: только один конкурентный обработчик — passed.
- `schema_version` записан — passed.

### План отката

Миграция только добавляет таблицы/колонки; откат — восстановление бэкапа БД,
созданного до обновления (механизм `backup_manager.restore_from_file`).

### Инварианты

- Оба panel users создаются с одним `telegramId`; ответ панели проверяется
  (`_create_panel_user` бросает `HybridCreationError` при несовпадении).
- `wifi → primary`, `lte → hybrid` — реализовано в `traffic_service.resolve_target`.

## Этап 4: Логика докупки WiFi/LTE трафика

**Статус: готово.**

### Изменённые/добавленные файлы

| Файл | Назначение |
|---|---|
| `src/shop_bot/modules/traffic_service.py` (новый) | Публичные операции: `available_traffic_types`, `resolve_target`, `calculate_price`, `validate_before_payment`, `create_purchase_draft`, `fulfill_traffic_purchase`, `credit_gb`, `manual_adjustment`, `compute_carry_after`, `perform_reset`, `run_daily_resets`, `burn_expired_carry`, `get_key_traffic_stats` |

### Формулы

- Цена: пакет — зафиксированная цена; произвольный объём — `gb * price_per_gb`;
  количество — целое 1..1000; скидка реферала только при
  `referral_discount_applies_to_traffic=1`; всё фиксируется в `traffic_purchases`
  до оплаты (`unit_price_rub`, `total_price_rub`, `discount_rub`).
- Пересчёт ГБ→байты только в `utils_common.gb_to_bytes`.
- Остаток переноса: `carry_after = max(0, min(carry_before, limit_before − max(base, used)))`;
  после reset лимит = `base_gb + carry_after`; байты округляются вниз до целых ГБ
  только в момент сохранения carry.
- Индивидуальный reset: дата от создания/последнего продления; пропущенные даты
  обрабатываются по возрастанию; идемпотентность — ключ
  `reset:{key_id}:{role}:{YYYY-MM-DD}` (UNIQUE в `traffic_operations`).
- Истечение: `burn_expired_carry` — carry обнуляется, audit `expiry_burn`.
- Базовый лимит — из `vpn_keys.traffic_limit_bytes` (snapshot); при отсутствии —
  `manual_review` в журнале, значение не угадывается.

### Тесты (`tests/test_traffic_service.py`)

- WiFi → primary, LTE → hybrid — passed.
- LTE не появляется без пары / при `hybrid_enabled=0` / при выключенной докупке — passed.
- Границы ввода: 0, 1001, −5, «1.5» отклоняются — passed.
- Пакетная и произвольная цена; отсутствие цены — ошибка — passed.
- Формула carry: (50,25,75,10)→25; (50,25,75,75)→0; (50,25,75,60)→15 — passed.
- **Пример из ТЗ:** база 50 ГБ, carry 25 ГБ, использовано 10 ГБ → после reset лимит
  75 ГБ (применено `gb_to_bytes(75)`); повторный reset той же даты — skipped, ровно
  один API-вызов; после расхода всех 75 ГБ следующий reset возвращает 50 ГБ, carry=0 — passed.
- Истечение подписки очищает carry (аудит `expiry_burn`; повтор — no-op) — passed.

### Технические исправления при реализации политики приёма

1. `run_migration()`: блок нового домена (`_ensure_traffic_tables`,
   `_ensure_fulfillment_tables`, `_ensure_backup_snapshot_tables`,
   `_ensure_schema_version`) выполняется **первым и в отдельной транзакции**;
   каждый legacy-шаг изолирован (`_legacy_step`: сбой шага откатывает только его,
   остальные продолжаются). Раньше падение на отсутствующей `button_configs`
   откатывало всю транзакцию, включая новые таблицы и данные.
2. `_ensure_fulfillment_tables` создаёт `pending_transactions`, если её нет
   (старые бэкапы), перед `ALTER`.
3. `_ensure_schema_version` — upsert с повышением версии только вперёд
   (`ON CONFLICT ... WHERE old < new`).
4. `restore_from_file` возвращает `(ok, message)`; пишет audit в
   `bot_settings.last_restore_info`; контрольная валидация после миграции.
5. Flask `/admin/db/restore`: читает `allow_incomplete` из формы, различает
   success/warning/danger flash. В UI (settings.html) добавлен чекбокс
   «Разрешить восстановление неполного/старого бэкапа».

### Поведение при загрузке старой БД (инцидент из логов)

Было: `WARNING ... схема БД (0) старее минимально поддерживаемой (2)` →
`ERROR ... файл БД не прошёл проверку` → отказ.
Стало: WARNING со списком недостающих таблиц → БД принимается как основная →
`src.backup` → миграция вперёд (новые таблицы + schema_version=2) → flash
«Восстановление выполнено с предупреждением: Загружена БД СТАРОЙ версии …
принята как основная и мигрирована к текущей схеме; данные пользователей
сохранены, функции нового домена включены».

1. **Нет живого тестового хоста Remnawave** в окружении исполнителя: API-контракт
   проверен по коду и мокам; перед включением гибрида на production обязательно
   выполнить контрольные запросы на тестовой панели (Этап 0, п.2 ТЗ) и
   подтвердить семантику `traffic_limit_gb=0` как неограниченного лимита (раздел 4.2 ТЗ).

   блока в users.html — следующая итерация.
4. **Деплой**: перед запуском выполнить `initialize_db()`/`run_migration()` (миграция
   идемпотентна), убедиться в установке зависимостей (`paramiko`, `aiogram` и пр.).
5. **Реферальный процент для трафика** использует общую настройку
   `referral_percentage` (ТЗ, Этап 6, п.2); отдельной per-traffic ставки нет.

### Доработка 11. Перенос ключей между хостами (server migration)

**Новый модуль `server_migration.py`** реализует перенос подписок пользователей
с одного хоста Remnawave на другой. Поддерживаемые сценарии:

**Форматы переноса (mode):**
1. `all` — перенос всех ключей с исходного хоста на целевой.
2. `user` — перенос конкретного пользователя (по Telegram ID или username):
   одна или несколько его подписок на исходном хосте.
3. `specific` — перенос конкретных подписок (по key_id, список через запятую).

**Выбор роли (role):** админ в UI указывает, какую роль выполнял ключ на
исходном хосте — `wifi` (основной) или `lte` (дополнительный). Это определяет,
на какого пользователя переносить данные использованного трафика при
включённом гибриде на целевом хосте.

**Алгоритм для каждого ключа:**
1. **Запомнить параметры:** remnawave_user_id старого ключа, usedTrafficBytes,
   trafficLimitBytes, expire_at.
2. **Удалить старый ключ** из панели Remnawave исходного хоста.
3. **Вычислить лимит для нового хоста:**
   - `target_base` = базовый лимит из тарифа целевого хоста;
   - если `old_limit > target_base` → `new_limit = old_limit`; излишек
     `(old_limit - target_base)` конвертируется в ГБ (округление вниз) и
     записывается как **несгораемый carry-баланс**;
   - если `old_limit < target_base` → `new_limit = target_base` (лимит
     повышается до нормы целевого хоста);
   - если `old_limit == target_base` → без изменений.
4. **Создать нового пользователя** на целевом хосте:
   - если `hybrid_enabled=1` → `create_hybrid_subscription` (primary + hybrid);
   - иначе → `create_or_update_key_on_host`.
5. **Обновить `vpn_keys`**: сменить `host_name`, `remnawave_user_uuid`,
   `subscription_url`, `traffic_limit_bytes`.
6. **Записать carry и audit** (операция `manual_adjustment` с деталями переноса).
7. **Перенести срок действия** — expire_at старого ключа передаётся в
   `ensure_user` / `create_hybrid_subscription`.

**API-маршруты (Flask):**
- `POST /server-migration/start` — параметры: `source_host`, `target_host`,
  `mode`, `telegram_id`, `key_ids`, `role`.
- `POST /server-migration/pause`
- `POST /server-migration/resume`
- `GET /server-migration/status`

**Scheduler:** `_maybe_run_server_migration()` вызывает `run_migration_batch()`
на каждом тике (300с), обрабатывая по 10 ключей за проход.

**UI в админке:** в карточку каждого хоста добавлен блок «Перенос ключей на
этот хост» с:
- dropdown выбора исходного хоста;
- dropdown формата (все / пользователь / конкретные подписки);
- полем Telegram ID/username (при mode=user);
- полем key_id через запятую (при mode=specific);
- dropdown роли (WiFi/LTE) с пояснением;
- кнопками «Запустить/Пауза/Продолжить/Обновить»;
- бейджем статуса и прогресс-блоком.

### Доработка 12. FIX: traffic_purchase вёл к выдаче ключа (критичный)

**Симптом (логи):** после оплаты докупки ГБ через YooMoney и нажатия «Проверить

**Причина:** после перевода докупки на общий FSM `PaymentProcess` подтверждение
`YooMoney Check` и `Stars Success` проходили через
`process_successful_payment`, который обрабатывал `traffic_purchase` как
обычное продление подписки.

**Решение:**
1. `process_successful_payment`: в начале добавлена ветка — при
   `action == "traffic_purchase"` платёж передаётся в
   `fulfillment.confirm_payment_and_enqueue` и функция возвращается
   (никакой выдачи ключа).
2. `check_pending_payment_handler` («🔄 Проверить оплату»): при
   `traffic_purchase` — вызов fulfillment напрямую + ответ
   «Гигабайты начисляются».
3. `stars_success_handler`: при `traffic_purchase` — fulfillment напрямую.

### Доработка 15. Идентификация клиента по panel telegramId (полная цепочка)

**Требование владельца:** при создании ключа панель хранит Telegram ID; при
выдаче ключа клиенту бот обязан сверить `telegramId` панельного пользователя с
Telegram ID клиента — совпало → выдать ссылку, нет → не выдавать и искать
дальше. То же при автоматическом и админском удалении.

**Было:** сверка `telegramId` была только в гибридном saga
(`hybrid_service._create_panel_user`); обычные ключи, триал, автоудаление и
админское удаление сверку не выполняли. В карточке ключа сверялся только panel
`id`, но не `telegramId`.

**Решение — проверка добавлена во все точки:**

1. **Выдача нового ключа** (`process_successful_payment`, action=new,
   non-hybrid): после `create_or_update_key_on_host` сверяется
   `payload.telegramId` с `uid`. При несовпадении:
   - audit `identity_mismatch_new` + лог `IDENTITY MISMATCH`;
   - ищется панельный пользователь с правильным telegramId через новую
     функцию `remnawave_api.find_panel_user_by_telegram_id()` (по squad'ам хоста);
   - найден → данные ключа подменяются на корректного пользователя (выдаётся
     правильная ссылка); не найден → `res=None` → возврат средств, ключ не выдаётся.

2. **Карточка ключа** (`refresh_key_info_internal`): помимо существующей
   сверки panel `id`, добавлена сверка `remote_user.telegramId` с владельцем
   `user_id`. При несовпадении — ссылка не выводится, показывается заглушка
   «Временная ошибка синхронизации», audit `identity_mismatch_card`.

3. **Триал** (`process_trial_key_creation`): сверка `telegramId` в ответе
   панели с Telegram ID пользователя. При несовпадении — ключ не создаётся,
   `set_trial_used` не вызывается (попытка не сгорает), сообщение об ошибке.

4. **Автоудаление** (`scheduler.sync_keys_with_panels`): перед удалением
   просроченного ключа сверяется `telegramId` панельного пользователя с
   владельцем в БД. При несовпадении — панельный аккаунт НЕ удаляется
   (защита от удаления чужого аккаунта), audit `identity_mismatch_delete`,
   ключ удаляется только локально.

5. **Админское удаление** (`/admin/keys/<id>/delete`): перед удалением из
   панели читается `telegramId` через `get_user_by_id` и сверяется с
   владельцем. При несовпадении — удаление из панели НЕ выполняется (flash
   предупреждение админу), ключ удаляется только из БД бота, audit
   `identity_mismatch_admin_delete`.

6. **API**: `create_or_update_key_on_host` теперь возвращает `telegramId`
   из ответа панели; добавлены helpers `_panel_telegram_id_matches` /
   `_panel_telegram_id_problems` и функция поиска
   `find_panel_user_by_telegram_id(host_name, telegram_id)`.

Примечание: если панель не хранит `telegramId` (пусто/None) — проверка
считается пройденной (нет данных для сравнения), чтобы не блокировать работу
на конфигурациях без этого поля.
